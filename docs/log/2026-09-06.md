- **Contracts chain.** `z.toJSONSchema(z.globalRegistry)` emits one `contracts.json` with `$defs` and
  `$ref`s between contracts; `datamodel-code-generator` 0.76 turns it into one pydantic module. Both
  directions have a `:check` that fails on drift.
- **Schema owner and isolation suite.** Drizzle config, an advisory-locked migration runner, and
  `isolation.test.ts`, which asserts every table in `public` has RLS enabled and forced, at least one
  policy, and an `organization_id` column, and that the app role can never bypass RLS. Vacuously true
  today (zero tables), and the first S1 table without those facts fails the gate.
- **Local gate and verified delivery.** `pnpm ci:local` validates the exact clean commit and writes a
  receipt under `.git/local-ci/`; `pnpm push:verified` / `pnpm pr:verified` publish a `local-ci` status

- **Docs.** AGENTS.md working rules (git, environments, local dev, tenancy, contracts, Python, UI,

## How

The one mechanism worth explaining: the scope never comes from the request. `resolveScope()` is one
function in the web app; today it returns the seeded organization and user from the contracts package,
and at S24 Better Auth replaces its body. The hello workflow exists to prove the organization id
crosses the language seam intact: the Python activity copies it from the input and the Zod output
schema refuses anything else. The isolation suite is the other half of the same idea, built before the
first table so a table without forced RLS cannot be merged.

## Went wrong

- **pnpm 10 cannot self-switch to pnpm 12.** The `packageManager` field made the installed pnpm 10
  download 12.3.4's npm tarball and fail with `ENOEXEC`, because 12 is a native binary behind a shell
  launcher. The official installer put 12 under `~/Library/pnpm/bin`; the shell sessions opened before
  that still resolve the old binary, which is how the shadcn CLI failed three times before I noticed.
- **pnpm 12 renamed the build allow-list.** `onlyBuiltDependencies` is gone; the key is `allowBuilds`
  and a failed install writes a placeholder block into `pnpm-workspace.yaml`, which I then duplicated.
- **The 24-hour release-age gate bit on day one.** Playwright 1.63.0 was published at 22:44 UTC on
  2026-09-04, inside the window. Pinned 1.62.1 as the tech stack said. Vitest 5.0.0 (2026-09-03)
  passed the gate and was adopted; it is a sprint boundary.
- **Moving a uv project breaks its virtualenv.** Every script in `.venv/bin` embeds the interpreter's
  absolute path in its shebang; after the move, `pyright` and `pytest` failed with "No such file" while
  `ruff`, a native binary, kept working. Deleted the venv and synced again. I also ran two `uv`
  commands on the same project concurrently once, which is a race; the rule is now written down.
- **Temporal needs the contract types at runtime.** ruff's TC001 asked me to move the pydantic model
  imports into a `TYPE_CHECKING` block; the SDK resolves the run method's type hints to deserialise
  payloads, so the workflow test failed with `NameError`. The imports stay real, with a comment.
- **pydantic refuses a regex on a UUID.** Zod emits both `format: uuid` and a `pattern` for
  `z.uuid()`; datamodel-codegen typed the field `UUID` and attached the pattern, which pydantic rejects
  at import time. The emitter now strips `pattern` wherever `format` is `uuid`.
- **Ultracite's first fix pass reformatted the design prototypes under `docs/`.** 589 findings, almost
  all in `temnia-studio.html`. Reverted from git and excluded `docs`, the vendored `components/ui`,
  and both generated folders from Biome.
- **The web image's pnpm download failed inside Docker.** GitHub's release CDN refused the connection
  from the build VM; the pipeline image, which installs uv from a GHCR image, built fine at 304 MB.
  Fixed by installing pnpm from the npm registry inside the image (its package carries the musl
  binary as an optional dependency): 4.9 s, and no GitHub URL in the build.
- **`docker compose up --wait` exits 1 once a one-shot job has finished.** The schema and namespace
  jobs exit 0 by design; compose counts them as failed anyway, which the gate surfaced on its second
  run. The wait set now names the four long-running services (`pnpm services`).
- **`turbo prune --docker` leaves root config files behind.** The pruned context had every workspace
  package but not `tsconfig.base.json`, so Turbopack failed to resolve `extends` and the web image
  build died on the gate's third run. One explicit `COPY` in the installer stage.
- **The verified-PR script asked GitHub for a workflow that did not exist yet.** `gh run list
  --workflow ci.yml` resolves the file on the default branch, and this PR is the one that adds it, so
  the wait after opening PR #3 failed while the check itself had already passed in 6 s. The lookup now
  goes by commit and workflow name.
- **Temporal's images have no bash.** The schema job died at `exec: /bin/bash`. Rewritten for `sh`,
  health check on `nc -z`.
- **The shell kept the working directory of the previous command.** Three separate mistakes came
  from it: root files written into `apps/web`, the pipeline scaffolded at `apps/web/apps/pipeline`,
  and shadcn run from the wrong directory. Every command now starts with an absolute `cd`.

### X 2 (how it works: the stack)

Day 1, part 2. How the stack got decided, because this is where I interfered the most.

I have an older repo for this product. 120 commits, a walking skeleton, then it failed its first real gate at 18% clip acceptance. When I asked Claude Code for a stack for the rebuild, its first draft carried most of the old repo's choices forward by default. Reasonable, and exactly what I didn't want, because half of those were made under constraints that no longer exist.

So I made it a rule in the repo: the old codebase is reference only. Every slot gets researched against what exists today, and the old choice can win, but only if the comparison says so. It re-researched around 70 slots. 25 came out different. The local S3 store I'd been using had been archived in April without me noticing, so it's Garage now. Trigger.dev plus Temporal became Temporal only, after checking that worker versioning and task-queue fairness went GA this year. TypeScript 7 native, since Next runs it.

Two things it proposed that I overruled. It wanted Lucide icons, less friction with the component registry. I kept Hugeicons because I like how they look, and not every decision needs a benchmark. It had a hosted transcription vendor first with WhisperX as a later A/B. I put WhisperX on Modal first, because the one independent benchmark on podcast audio I trust has it ahead.

The bigger interference was the sprint plan. Its first draft had 25 sprints with the editing work pushed behind a private alpha. I flipped it: every editing feature first, then everything that turns it into a multi-tenant product. No login screen until the editor is done. 38 sprints, 6 gates, first real gate at sprint 5, the chapter cut, the thing that scored 18% last time.

### X 5 (went wrong: the password)

Day 1, part 5, the one I'd rather not post.

While creating the database on staging, the agent made an ad-hoc API call and the response echoed the whole database record, generated password included, into its own transcript. It noticed straight away, generated a new password on the server, changed it in Postgres and in Dokploy's record, and verified that the old one no longer worked.

Except the verification was wrong. It tested from inside the database container, and the official image trusts logins from inside the container, so the old and the new password both "worked". It caught that too, retested from a separate container over the Docker network, and only then did the old password get rejected.

The database isn't reachable from the internet and nothing lives in it yet. Still. Two rules came out of it, both in the repo now: never print a database record from that API, and verify a rotation from outside the container. I'm posting it because the premise of this series is that you get the failures the day they happen.

### LinkedIn 3 (how it works: the fence)

Building Temnia in public, day 1, one decision an agency should care about.

If you run several clients through one tool, the question to ask its maker is: what physically stops client A's data from showing up in client B's screen? Not "do you have permissions". What stops it.

In Temnia the answer is the database engine. Every table is fenced to one organisation by Postgres itself, not by application code remembering to add a filter. And the test for that fence exists before the first table does. It reads the database catalogue and fails the build the moment any table lacks the fence. Today it passes with zero tables, which sounds like a joke and isn't: the first table without a fence can't be merged, by anyone, including the agent that writes most of the code.

There's no login screen yet. The fence is there first. That order is deliberate, and it's the kind of thing you can only decide at the start.
