## How

Uppy 6's plugin reads a `s3Multipart` field on the file (the state Golden Retriever persists) and,
when it finds one, forces multipart and resumes through ListParts. That is the whole trick: the
server creates the multipart as before and knows the UploadId from the first second, and the browser
only has to be told. Everything the S1 client was kept for (server-side truth for resume, the grace
window, the reaper's liveness rule) survives unchanged; what changed is who drives the PUTs.

reason it belongs there rather than in a hotfix. One I want to remember: two people correcting the
same transcript both computed the same next revision number and uploaded to the same object key.
The database correctly refused the second save as stale, but its bytes were already sitting behind
the first person's accepted pointer. The fix: every attempt writes its own object, one
compare-and-swap publishes exactly one of them, and readers take the key from the row instead of
rebuilding it from a number. Nothing is verified on a real GPU tonight. There is a smoke test for
that now, and it runs after the next deploy.
